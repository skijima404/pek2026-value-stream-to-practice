# 仮ストーリー

## この記録の位置づけ

2026年9月14日の人間とCodexの対話で組み立てた、登壇ストーリーの暫定案を保存する。
実践者が「一旦仮のストーリーとしておく」と指定した時点の記録である。
既存資料を後から統合して新しい検証済みの主張を作るものではなく、この対話での
構成判断と発展中の考えを記録するRaw Noteである。

完成した台本、スライド、採用済みArtifactではない。保存の許可と、この整理済み本文への
意図確認は区別し、保存時点では`unreviewed`とする。

## 中心となる流れ

```text
受け手の体験
  → 品質だけでは受け手の体験は決まらない
  → Adoptionと仕事の受け渡しの設計
  → 仮説検証
  → VSM・MBPMと担当者所感による問題の理解
  → 困りごとに応じたAIの使い方とSolutionの選択
  → 期待効果と歪みの両方を計測し、判断を更新する
```

直近の対話で、次の三段階を混ぜないことを明確にした。

| 段階 | 確認すること | 方法 |
| --- | --- | --- |
| 改善対象と困りごとを見つける | 誰が何に困っていて、どこを改善すると価値がありそうか | VSM・MBPMにマジカのカードなどで拾った担当者所感を重ねて分析する |
| 妥当なSolutionを考える | AIを使うなら、その困りごとにどんな使い方が有用か。このSolutionで改善できるという見立ては妥当か | 必要な品質、AIから欲しいOutcome、委譲範囲とSolution候補を確認する |
| 効果と歪みを確かめる | 本当に有用なSolutionだったか。その先に負担や歪みを生んでいないか | 期待効果が出る場所と歪みが起きそうな場所の両方にメトリックを置く |

## 1. 挙手で送り手と受け手の経験を共有する

冒頭で、次の二つを尋ねる案。

- 「AI Slopの被害を受けたことがある方？」
- 「自分が作ったものをAI Slopだと指摘されたことがある方？」

どちらの立場にもなり得ることを共有し、実践者自身の、他の人が生成AIで資料作成を
代行した結果、後続レビューに時間がかかった経験へつなぐ。

対話で即興的に挙げた「通常2時間」「3倍・4倍」は、本人が適当に述べた数字と明示したため、
登壇で使う確定値にはしない。既存の提案書事例を使う場合は、その記録に合わせる。

Meat Proxyは、挙手した参加者へ非難の矛先が向くように聞こえる可能性を考え、
今回の冒頭から外す方向とした。

## 2. 受け手には何が起きているのか：Workslop調査

つなぎの問いは「では、AI Slopを受け取ったという人には、何が起きているのでしょうか？」。

BetterUpとStanford Social Media LabのWorkslop調査から、受け手に解釈、確認、補完、
修正の仕事が残り、フラストレーションや送り手への信頼にも影響が報告されていることを紹介する。
これは米国のデスクワーカーの自己申告を扱う調査であり、一般的な因果や日本のPlatform利用者の
実態を直接示すものとしては扱わない。

加えて、BetterUp側が、使い手の習慣、判断、文脈の共有、責任、および組織の支援を
問題にしていることを紹介する。そこから、以前からある仕事の受け渡しの問題としても
捉え直せる、という登壇者の解釈へ広げる。

「AIとは無関係と実証された」「Workslop調査は品質を扱っていない」とは説明しない。
調査はAI生成物を対象とし、低品質や目的との不適合にも言及している。

参照する既存記録：
`OBS-20260805-001807-workslop-recipient-burden`、
`EXT-20260804-144101-betterup-workslop-recipient-experience`。

この対話で実際に確認した著者側の説明：

- [BetterUp共同創業者による、習慣・行動・対話についての寄稿](https://www.weforum.org/stories/leadership/why-ai-performance-depends-on-how-we-think-talk-and-lead/)
- [判断を働かせる使い方と、出力をそのまま承認する使い方を対比したBetterUp記事](https://www.betterup.com/blog/ai-washing-workslop)

これらの著者の説明と、受け手の自己申告調査の結果は区別する。

## 3. 良いものでも受け手には負担になる

つなぎの問いは「では、送り手がちゃんと考えて、有用なものを渡したら、問題は起こらないのでしょうか？」。

アウトプット品質と受け手のSlop経験を分ける、説明用のマトリクスを示す。

|  | 受け手がSlopと感じない | 受け手がSlopと感じる |
| --- | --- | --- |
| 品質が高い | 活用でき、仕事が進む | 有用でも、整理・学習・追加判断などの負担が生じる |
| 品質が低い | 不備や負担がまだ表れていない場合もある | 確認・修正・補完が必要になる |

これは体験を考えるための構成案であり、四領域の実測分布や二軸の無相関を示すものではない。
主役は「品質が高いのに、受け手に負担が生じる」領域とする。

実践者は「良い提案でも負担になる」話を入れたいと明示した。有用な提案でも、現在の成果物に
混ざると整理、判断、レビュー、責任を引き受ける仕事が増えることを示す。
対話ではスライドの話を置く案も挙がったが、本編で使う具体例と表現は今後整える。

具体的な既存候補は`RN-20260826-120311-ai-outcome-scope-control-reasoning-review`。
この事例はスライド生成ではなく、要件のIntentの論理検査に追加Optionが混ざった話である。
両者を同一事例に書き換えない。

## 4. Adoptionとバトンパス

実践者は、トランスフォーメーションやプロセス効率化の仕事を長く行ってきた経験から、
良いSolutionやPracticeを導入しても、実際の活用にはAdoptionが重要だと説明した。

ここで扱うAdoptionは、広報やEnablementに加え、新しいものの導入によって既存プロセスの
どこに歪みが出たかを見つけ、その歪みを丁寧に解消していく活動である。
受け手が納得して受け取れること、実際に使えることを論点にする。

バトンパスの比喩へつなぐ。バトンの品質や送り手の走る速さだけでは受け渡しは成立しない。
受け手の位置、速度、タイミングなどを合わせる必要がある。
受け手への説明だけでなく、役割、手順、処理可能な量、学習や判断の条件も検討する構成案とする。

## 5. 仮説検証という言葉を置く

「では、うまくいっているか、問題がないかをどう確かめるのでしょうか？」。
続けて「仮説検証って、なんとなく知っているよ、という方？」と尋ねる案。

今回扱う意味を短く説明する。

> このサービスで誰のどの仕事が良くなるはずか。一方、その先のどこに新しい負担が
> 生じそうか。こうした見立てを置き、確かめ、続ける・変える・やめるを判断する。

AIが回答できたことに加え、その回答を使う人の仕事が良くなったかまで確認する。
ここでは話の共通言語を揃え、具体的な進め方は後半の例で示す。

## 6. VSM・MBPMを使う理由

VSMで対象Journeyの全体を捉え、必要な箇所をMBPMで掘り下げる。
誰が何を受け取り、判断し、次へ渡すのか。実作業、着手待ち、確認、手戻りを分けて見る。

ただし、図や時間のMetricだけで改善対象を決めない。担当者の工夫や違和感も拾い、
本当に困っていることを確認する。その具体的な方法として、後半でマジカのカードを示す。

VSM・MBPMは、問題の理解、Solutionの影響範囲の検討、メトリックの配置に使う道具とする。
図を描いたこと自体を、原因の特定やSolutionの有効性の検証とは扱わない。

## 7. Lead Timeと反復量：狙う成果に合わせて時間を見る

二つの話を対にして使うことを、実践者が選んだ。

| 話 | 説明すること | 元の記録 |
| --- | --- | --- |
| Waterfall組織でVSMを作成した経験 | 開発の占める期間を見て、開発高速化が期待する全体のLead Time短縮にどれだけ効くかを問い直す | `RN-20260914-204312-waterfall-vsm-lead-time-and-cost` |
| 戦略判断からDeliveryへの反復量モデル | 同じ5分でも、実行回数と利用チーム数によって総工数への影響が変わる | `RN-20260818-203016-strategy-to-delivery-repetition-model` |

Lead Time削減と工数・コスト削減を混ぜない。開発高速化の全体期間への効果が限定的でも、
反復される作業の総工数削減には価値がある場合を説明する。工数削減をそのまま金銭的な
コスト削減量へ換算しない。

上流の判断では判断の質、反復の多い活動では一回あたりの負荷にも着目する。
「EA活動はすべて数年に一度」「下流ほど必ず価値が大きい」という一般則にはしない。
反復量モデルの数値は説明用の仮定で、Waterfall事例の経験とは区別する。

## 8. Platform Advisorで三段階を具体化する

「では、サンプルのPlatform Serviceで、具体的な使い方を説明しましょう」。
Platform Advisorは説明用の架空Scenarioであり、実在の導入成果として提示しない。

### 8-1. 改善対象と困りごとを見つける

利用者が情報を探し、比較し、選定し、利用開始する流れをVSMで示し、必要な受け渡しを
MBPMで掘り下げる。周囲に担当者の所感や工夫を置いて分析する。

この対話で実践者は、マジカフレームワークの一部として、次の二種類のカードをVSMの
周りに置いてもらっていると説明し、カード画像を提示した。

- 「もやもや」：もやもやすることを記入するカード。
- 「技あり」：「実はこんな工夫をしてます」と、工夫を記入するカード。

実践者は、カードの見栄えが分かりやすく、情報の吸い上げに非常に役立つと述べた。
属人化している箇所やVSMには現れない問題が出てくるため、VSMと担当者所感を合わせて
AI投入箇所を検討しているという。これは実践者が報告した使用経験であり、
カードの有無による比較測定の結果ではない。

手順の一部は既に`RN-20260802-211319-textbook-hypothesis-flow-and-solution-first-reconstruction`と
`RN-20260806-224717-vsm-mbpm-process-analysis-explanation`に記録されている。
マジカの二種類のカードを使用していることと、視覚的な分かりやすさへの評価は、今回の補足である。
カード画像そのものは本ノートへ複製していない。版や公式配布元の確認は未実施である。

### 8-2. 困りごとに妥当なAIの使い方とSolutionを選ぶ

まず、誰が本当に何に困っているのか、どうなれば助かるのか、どの品質を保つ必要があるかを確認する。
AIを使うなら、その困りごとに有用な使い方を選ぶ。

次の対応は説明用の例であり、実際の担当者の発言や検証結果ではない。

| 困りごとの例 | AIから欲しいOutcome |
| --- | --- |
| 情報が散らばっていて見つからない | 広く探す |
| 資料と自分たちの状況との関係が分からない | 分かるように解釈する |
| 比較観点を毎回有識者が組み立てている | 選べるように整理する |
| 選定理由の抜けや矛盾を確認したい | 本当に筋が通るか疑う |
| 判断済みの内容を繰り返し転記している | 速く作る |

五つのOutcomeは`RN-20260730-140133-ai-outcomes-and-mbpm`にある登壇用の分類候補を使う。
網羅的・排他的なAI能力分類としては扱わない。

「筋が通るか疑ってほしい」場面に追加Optionが混ざると、有用でも別の判断作業が生じるという
冒頭の例をここで回収できる。欲しいOutcomeは、委譲範囲とレビュー範囲を揃えるためにも使う。

Solutionを選んだ理由と、困りごとを改善できるはずだという仮説を明示する。
AIを使うことを先に成功条件とせず、AIに任せる範囲と、人間や既存の仕組みが担う範囲を考える。

### 8-3. 期待効果と歪みの両方を計測する

効果が出ると期待する場所と、新しい負担や歪みが起きそうな場所の両方にメトリックを置く。

| 観測する側 | Platform Advisorで扱う候補 |
| --- | --- |
| 狙った効果 | 情報探索、問い合わせ、比較観点整理の時間、判断材料の充足、次の作業へ進めるか |
| 歪みや負荷移転 | 後続レビュー時間、追加問い合わせ、差し戻し、適合性の再確認、選び直し |

「本当に有用なSolutionだったか」と「その先に歪みを生んでいないか」を確かめる。
期待する変化と見直す条件を置き、結果をもとに継続、修正、停止、追加検証を判断する。
局所の時間短縮やPlatform採用が、そのまま最終的なBusiness Outcomeの実現を意味するとはしない。

既存のScenarioと観測設計を具体化する際の参照先：
`RN-20260806-014446-platform-advisor-business-goal-and-blind-spot`、
`RN-20260806-210946-platform-advisor-fictional-validation`、
`RN-20260807-123008-platform-advisor-effect-measurement-observation-rationale`。
既存の物語内検証やBlind Spotを本編へどこまで含めるかは、この対話では確定していない。

## 9. 持ち帰る実践

自分たちのPlatform Serviceの流れを一つ選び、担当者の困りごとや工夫も聞く。
誰のどの仕事をどう良くしたいか、そのためにどんなSolutionやAIの使い方が妥当かを考える。
効果が出る場所と歪みが出そうな場所を挙げ、それぞれを確かめるメトリックを置く。

この一連を、小さく始められる仮説検証として持ち帰ってもらう構成案とする。
