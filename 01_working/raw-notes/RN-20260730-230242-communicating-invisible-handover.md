# メモ

## 出発点

長くLeanやプロセス改善に関わる中で、ハンドオーバーは常に重要だと
考えてきた。

> ハンドオーバーの目的は、作業を終えて成果物を渡すことではない。
> 価値を積み上げ、次の作業者が問題なく作業を遂行できる状態を整えて
> 渡すことである。

しかし、この考えはなかなか伝わらない。

今回のセッションでは、AI Slop、リレーのバトンパス、User Story、
Acceptance Criteria、VSMをつなぐことで、抽象的な「連携が重要」という
話ではなく、観測可能な因果と設計方法として伝えたい。

## ハンドオーバーの完了条件

ハンドオーバーの完了条件は、渡し手側の「作業が終わった」ではない。

```text
作業中心

自分の成果物が完成した
  ↓
相手へ渡した
  ↓
自分の担当は終了
```

Outcome中心では、受け手が次へ進めるところまでを見る。

```text
次の作業者が必要とする状態を定義する
  ↓
成果物、Context、判断根拠、責任を整える
  ↓
受け手が理解する
  ↓
次の作業を開始し、問題なく遂行できる
  ↓
Value Streamが流れ続ける
```

中心となる表現:

> ハンドオーバーの成否は、渡した側ではなく、受け取った側が次に
> 進めたかで決まる。

> 次の走者が走り続けられる条件を、走り方より先に決める。

## なぜ重要性が見えにくいのか

ハンドオーバーの品質は二つのチームの間にあるため、どちらの成果としても
計上されにくい。

```text
渡し手
「成果物を完成させた」

        ↓ 見えにくい領域

受け手
「受け取った成果物で仕事を進めた」
```

その間にある次の仕事は、誰のBacklogにも載らないことがある。

- Contextを理解できるようにする
- 判断根拠を引き継ぐ
- 未判断事項を明示する
- 責任の移動を確認する
- 例外時の戻し先を決める
- 次の仕事を開始できる権限と情報を揃える

組織の管理単位も、この不可視化を強める。

- 組織図は役割や専門性ごとに分かれる
- Backlogはチームごとに分かれる
- 予算はプロジェクトやシステムごとに置かれる
- KPIは作成数、完了数、処理時間へ寄りやすい
- Definition of Doneは自チーム内で閉じやすい
- 問題は境界で起こるが、改善は各チームの箱の中で行われる

Platform Team、Application Team、Operationsがそれぞれ自分の作業を
完了しても、利用者が安全に開発と運用を継続できるというトータルな
Outcomeには、単独の所有者がいない場合がある。

ハンドオーバーを整える仕事は、外から見ると会話、調整、説明、確認に見える。
目に見える成果物を作っていないように見えるため、ムダとして削られやすい。
しかし、実際にはその仕事がValue Streamを成立させている。

短い表現:

> 私たちは作業を組織化するのは得意だが、作業と作業の間を
> 組織化するのが苦手である。

> ハンドオーバーが軽視されるのは、重要でないからではない。
> 組織図にもBacklogにも現れないからである。

## AIが見えない境界問題を増幅する

AIは、チームの箱の中にある生成、実装、文書作成などを高速化する。

```text
箱の中の作業は爆速になる
  ↓
完了したOutputが大量に境界へ来る
  ↓
境界の理解、判断、責任移転は同じ速度のまま
  ↓
確認、待ち、差し戻しが増える
```

したがって、AI Slopが現れる場所は生成工程だけではない。

> AI Slopは、組織がもともと仕事として認識していなかった接点に現れる。

リレーの比喩では、AIで走者だけが速くなっても、バトンパスが
速くならなければ全体のタイムは縮まらない。

```text
AIで走者だけが速くなる
  ↓
バトンパスは速くならない
  ↓
受け渡し地点に成果物が滞留する
  ↓
全体のタイムは縮まらない
```

## User StoryとAcceptance Criteriaで具体化する

AgileのUser Storyは、利用者とのContractから作業Scopeを切る仕組みとして
説明できる。

```text
As a <誰が>
I want to <何を可能にしたい>
So that <どんなOutcomeを得たい>
```

User Storyは、誰が何を可能にし、なぜ次へ進みたいかを表す。

Acceptance Criteriaは、バトンパスが成立したと判断するためのルールになる。

- 必要な入力が揃っている
- 前提と制約が明確である
- 標準と例外の扱いが分かる
- 責任の移動が明確である
- 失敗時の戻し先が分かる
- 受け手が次の作業を開始できる

```text
User Story
  = 利用者とOutcome

Acceptance Criteria
  = バトンパス成立のルール

Implementation
  = そのルールを満たす走り方

VSM
  = 本当に全体が流れたかの観測
```

Acceptance Criteriaは、走り方そのものを固定する実装指示ではない。
次の走者が走り続けられる観測可能な境界条件を定義する。

## VSMで見るもの

VSMでは、前工程の作業完了だけでなく、受け手が次の作業を開始できたかを
観測する。

- 受領から次の作業開始までの時間
- 確認の往復回数
- 入力不備による差し戻し
- Contextの再探索時間
- 判断待ち
- 責任者や相談先の探索時間
- 後工程で判明した手戻り
- 利用者が意図したOutcomeへ到達したか

これにより、「作業が速くなった」と「価値が速く流れた」を分けて考えられる。

## セッションでの伝え方

これまでは「ハンドオーバーが重要」という抽象的な主張として伝わりにくかった
可能性がある。今回は次の順序で、因果、比喩、既知の実践、測定へつなぐ。

```text
AIで走者だけが速くなる
  ↓
バトンパスが詰まる
  ↓
ハンドオーバーは点ではなくオーバーラップする区間
  ↓
User Storyで利用者とOutcomeを定義する
  ↓
Acceptance Criteriaで受け渡し条件を定義する
  ↓
Contractから実装を逆算する
  ↓
VSMで次の走者が本当に進めたかを観測する
```

説明の核:

> AI時代に設計すべきなのは、速い作業だけではない。
> 次の人が走り続けられるバトンパスである。

補足:

> Platform Serviceを公開したことは、バトンを手放したことにすぎない。
> 利用者が次の仕事を遂行できて、初めてハンドオーバーが成立する。

## このセッション自体での検証

この説明が従来より伝わるかは、まだ検証されていない。

当日は次を観察候補とする。

- リレーの比喩でハンドオーバーの意味が伝わるか
- User StoryとAcceptance Criteriaとの対応で実務へ接続できるか
- 「受け手が次に進めたかが完了条件」という表現への反応
- AI Slopを生成品質ではなく境界問題として捉えられるか
- セッション後に参加者が自分のValue Stream上のハンドオーバーを
  説明できるか

伝わらなかった場合は、どこで理解が止まったかを観測し、
セッション側のContractと説明順序を更新する。
