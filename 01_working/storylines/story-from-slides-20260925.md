## 一本の流れ

> AIを使って仕事を速くしても、受け手が困ったり、全体の成果につながらなかったりすることがあります。
> 仕事の受け渡しと、目的への貢献・受け手の負荷を見ましょう。
> VSMとMBPMで仕事の流れを捉え、狙った改善が組織目的へつながる筋道を価値仮説にします。
> その筋道に沿って、狙った効果と悪い副作用の両方を測り、問題があれば原因を深掘りして対処します。

```text
受け取って困った経験／渡して否定的な反応を受けた経験
  → 自身の体験とWorkslop調査で、受け手に生じる負担を見る
  → AIの有無にかかわらず、仕事を渡す側には責任がある
  → バトンパスで、受け渡しの条件と全体の成果を考える
  → 目的への貢献度と受け手の負荷で、残す・支援する・やめるを考える
  → VSM・MBPMでPlatform選定の流れと問い合わせの負荷を見る
  → 「ミーティングゼロ」を目指し、価値仮説とPlatform Advisorを置く
  → ミーティングゼロだけでは成果・利用状況・副作用が分からない
  → 価値仮説に沿った効果、Adoption、後続工程・運用への副作用を測る
  → 測定で状態を知り、原因の深掘りを経て対処する
  → 価値仮説と効果測定で、AI Slopを検知・修正できるようにする
  → この資料の検討過程もRepoで公開していると案内する
```

## 1. 受け手・渡し手の両方から、AI Slopを自分の問題にする

**対応：p.1–7。**

表題と自己紹介の後、二つの問いで参加者の経験に接続する。AIの作業結果を受け取って困ったことがあるか。自分がAIで作ったものを渡し、否定的な反応を受けたことがあるか。送り手にも受け手にもなり得る話として始める。

続いて、自身のスライド作成に関するAI Slop体験を話す。p.6には「4h → 12h」が示されている。この図だけでは、時間の集計条件や作業内訳までは分からないため、書き起こしで具体的な内訳を補わない。

p.7ではBetterUpのWorkslop調査を紹介する。資料に載る数値は、直近1か月に受け取ったと認識する人が40%、1件あたりの対処が平均2時間、従業員1万人規模へ換算した年間の生産性損失が900万ドル。これはスライド記載の要約であり、この書き起こしで原調査を再検証したものではない。

同じページで、Slopかどうかは受け取り側の主観的な判定に依存し、成果物が本当に低品質だったかを調査内で評価したわけではない、という説明を置く。受け手が困ったという体験から、仕事の渡し方へ話を進める。

**次へのつながり：** 受け手に確認や補完が残るなら、AIの出力だけを見るのでは足りない。仕事を渡す側として何を確かめるかを考える。

## 2. バトンパスで受け渡しを捉え、対処の判断軸を置く

**対応：p.8–11。**

AIを使っても、仕事を後続へ渡す責任は変わらない。受け手が使える状態かを確認し、困りごとがあればフォローし、よりよい渡し方を考える。

それをリレーのバトンパスにたとえる。受け取った後すぐにトップスピードへ乗れたか、想定された区間で渡せたか、そして全体のタイムが出たか。p.9では、全体のタイムを最重要と強調している。

スピードが合わない、想定した場所にバトンがない、受け手の準備ができていない、といったずれがあると成果へつながらない。ただし、片方が悪いと決めつける話ではなく、実際の受け渡しを調べないと理由は分からない。

対処を考える軸として、目的への貢献度と受け手の負荷を組み合わせる。

| 貢献度 | 受け手の負荷 | スライドで示す方向 |
| --- | --- | --- |
| 高い | 低い | 理想の状態として残す |
| 高い | 高い | 改善・支援し、受け手がパンクしないようにして残す |
| 低い | 高い | 作らない、またはリタイアする。リリース済みなら即対応 |
| 低い | 低い | 成果へ貢献しないので作らない、またはリタイアする |

**次へのつながり：** 部分的に速くなっただけでは全体の成果は分からない。仕事の流れ全体を捉え、可視化・計測・改善するVSMへ進む。

## 3. Value Streamを説明し、先に「あるある」の事例を見せる

**対応：p.12–19。**

Value Streamを、価値が必要になってから必要な人へ届くまでの流れとして説明する。Value Stream Managementは、その流れを可視化・計測・改善する取り組みとして紹介する。「速かったか」「使えるものになったか」「後で問題が起きなかったか」という問いを、企画から運用までの図に載せる。

ここで、あるあるパターンを先に見せ、その後で解説すると予告する。以降のPlatform Advisorは説明用の架空事例であり、実在案件の成果報告ではない。

事例では、組織の目的、作戦、チームの目的を分ける。

- 組織は、限られた人的資源を価値創出へ集約したい。
- コンテナオーケストレーションによる運用の自動化・高度化を、そのための作戦とする。
- Platform Engineeringチームには、コンテナオーケストレーションの利用促進が求められている。

チームはまず、プラットフォームを選ぶまでの流れをVSMで捉える。情報収集、問い合わせ、比較観点の整理、意思決定、ADR記録、申請方法の調査・確認が並ぶ。

p.18で「わからない点をまとめて質問する」工程を、解決すべき課題の候補として指す。p.19ではMBPMを使ってその工程を拡大し、開発者、窓口担当、Enabling担当のやり取りを見る。事例の設定では、状況を把握して答えるためにミーティングが必要で、問い合わせのLTは1週間、再検討や追加質問による手戻りが50%とされる。

**次へのつながり：** この負荷を減らし、短時間で安全に選べるようにしたい。チームがどんな価値と目標、解決策を置くかを見せる。

## 4. 「ミーティングゼロ」と価値仮説、Platform Advisorを置く

**対応：p.21–23。p.20は旧案として除外。**

目指す価値は、プラットフォーム選定の負荷を軽減し、短時間で安全な選択を可能にすること。その目標として「ミーティングゼロ」を置く。

この局所の改善を組織の目的へつなぐ見込みを、価値仮説として見せる。

```text
情報収集・選定の負荷が減る
  → コンテナ基盤の採用が進む
  → 運用の自動化が進む
  → 人の手が空く
  → 必要な仕事へ人的資源を再配置できる
```

p.22の赤枠は、最初の二つを「このPlatform Engineeringチームのスコープ」として示している。組織目的までの見込みと、チームが直接担う範囲を区別する。

そのうえで、解決策としてPlatform Advisorを紹介する。AIチャットボットがプラットフォームの選び方、メリット・デメリット、技術を説明する。ミーティングの調整を減らし、開発者の理解度に合わせて説明することで、選定の負荷を減らそうとする。

**次へのつながり：** ここまでならもっともらしく見える。しかし、ミーティングがゼロになったら本当に成功なのか。ここから効果測定の解説へ入る。

## 5. 「ミーティングゼロ」の不足を、効果測定の問いへ変える

**対応：p.24–29。**

ミーティングゼロだけでは、欲しい成果が出たか、選定が進んだ結果なのかそもそも候補から外れたのか、副作用が出ていないかが分からない。

先ほどの二軸の図を再掲し、効果測定によって、成果への貢献と受け手の負荷のどこに該当するかを確かめると説明する。

効果測定を「活動目的に対するビジネス的なテストケース」にたとえる。

- 正常系：狙った効果が出ているか。
- 異常系：悪い副作用を抑えられているか。

まず正常系として、p.22の価値仮説をp.28で再掲する。同じつながりに確認の問いを載せる。

- チャットボットは情報収集の時間を短縮できているか。
- 情報収集が簡単になると、本当に基盤の採用が増えるか。
- 情報収集の時間短縮は、Value Stream全体の効率化につながっているか。

自動化に進む使われ方をしているか、作業工数が減るかという後続の問いも薄い色で残る。チームの直接の範囲を中心に話しながら、上位目的へつながる条件が別にあることを示す。

さらにAdoptionも確かめる。役立っているからミーティングがなくなったのか、基盤自体が無視されているからなくなったのかを区別するため、認知度、利用数、利用者の感想を見る。

**次へのつながり：** 狙った改善が起きても、別の人や工程が困っているかもしれない。次に異常系として副作用を見る。

## 6. 受け渡しと運用までを追い、副作用を見つける

**対応：p.30–32。**

価値仮説の図に、副作用を確かめる問いを重ねる。質の悪い回答が問題を起こしていないか。情報収集や選定の速度が急に変わって、困る人がいないか。

副作用を探す場所として、人と人とのハンドオーバーに着目する。p.31では、開発者の観点整理・資料作成から、承認者との意思決定へ進む図を使い、「承認が降りにくくなっていないか」と問う。問い合わせ窓口の工程とは別の、後続の受け渡しを見せている。

さらに、Value Streamの認識が短いと、リリース後の悪化を見落とす。p.32では企画から運用までの図に戻り、デプロイ時の想定外のトラブル、インシデント傾向、SLA実績、運用工数を確認対象として挙げる。

**次へのつながり：** 測定で良化・悪化を捉えられても、それだけで原因までは分からない。対処に進むには、もう一段深掘りする。

## 7. 状態の判定と原因の特定を分け、まとめへ進む

**対応：p.33–36。**

二軸の図をもう一度示し、効果測定で分かるのは「どこに該当するか」までだと区切る。

バトンパスの失敗例を再掲し、同じように受け渡しがうまくいかなくても、速度、位置、受け手の状態など理由は異なることを思い出してもらう。実際に何が起きたか、なぜ起きたかを深掘りし、その事象に合った対処をする。

まとめは、現行p.36の三点へ着地させる。

1. AI Slopを検知して修正できるよう警戒を怠らず、価値仮説と効果測定を利用する。
2. 目的へ至る因果のつながりを価値仮説として置き、効果や局所最適の有無を確かめられるようにする。
3. 効果測定では、狙った効果と悪い副作用の両方を測る。

以前の会話にあった「AI Slopは完全には防げない」を、現行PDFの見出しとして置き直さない。この版は、検知・修正できるようにする行動をまとめにしている。

## 8. 資料そのものの検討過程をRepoへつなぐ

**対応：p.37–38。**

どこでAIを使い、どう見直したかをたどれるように検討記録を公開していると紹介する。調査資料、話さなかったネタ、採用しなかった案も含むRepoへQRコードで案内し、Thank youで終える。記録が公開されていることを、AI Slopがないという保証にはしない。
