## 一本の流れ

> 良いものを作ったつもりでも、受け手の仕事が良くなるとは限りません。
> では、誰の何を改善するのか、どう引き渡すのか、どこを測れば確かめられるのか。
> VSMとMBPMを見ながら、一緒に考えてみましょう。

```text
受け手としてSlopを経験したことはあるか
  → 良い提案でも負担になる。Slopだからといって低品質とは限らない
  → 作り手の品質確認だけでは分からないので、受け手の仕事を確かめる
  → VSMで全体を捉え、MBPMと担当者の所感で問題と受け渡しを掘る
  → 本当の困りごとから、AIに求めるOutcomeと引き渡しのContractを決める【A 8-2】
  → 図のどこを見て、何を疑い、効果と歪みのどこを測るか説明する【D 6】
  → 小さく試し、計測結果と受け手の所感から続ける・変える・やめるを判断する
```

## 導入：Aの1〜3を主軸に、4を橋渡しにする

自己紹介では、トランスフォーメーションやプロセス効率化に携わってきたという本人の説明を使う。
肩書き・年数・実績数はここで補わない。

挙手は「AI Slopを受け取った経験」「自分が作ったものをそう指摘された経験」の両側を聞く。
自分自身の受け手の経験を続け、送り手への非難を主題にしない。Meat Proxyは入れない。

提案資料の例は、見栄えの良さに対し、実務で何を行うかや他のパートナーとの棲み分けが分からず、
確認・整理や従来の提案書の作り直しが必要だった、という負担の内容を短く話す。
`RN-20260804-195507-ai-proposal-review-burden-case`と、Bに保存した再作成の補足を参照する。
即興で述べた「通常2時間の3倍・4倍」は使わず、今回は時間の倍率より残った仕事を見せる。

Workslop調査は受け手が報告した解釈・確認・補完・修正の仕事を紹介する。
出典は`OBS-20260805-001807-workslop-recipient-burden`。米国デスクワーカーの自己申告であり、
AIと無関係だと証明した調査、品質を扱っていない調査、と説明しない。

その上で「では、有用な提案なら負担にはならないでしょうか」と問い、Aの品質とSlop経験の二軸を置く。
ここではIntentの論理検査に有用な追加Optionが混ざり、新たな判断・レビューが必要になった例を使う。
参照：`OBS-20260827-010635-ai-outcome-review-boundary`。提案資料の例とは別の出来事として説明する。
見栄えが良いだけの資料を「すべての意味で高品質だった」と扱わない。
二軸は説明用の整理であり、品質とSlop経験の無相関や各領域の実測分布を主張しない。

Adoptionは、導入で生まれた役割・手順・判断などの歪みを見つけ、解消する活動として短く置く。
バトンパスを独立した長い例にせず、必要なら一言の比喩に留める。

> 私たちだけで「Slopではありません」とは言い切れません。受け手の経験ですから。
> だから、どの仕事が良くなるはずか、その先で何が増えそうかを仮説にして、確かめます。
> ここからは、そのために図のどこを見て、どこを測るかをお話しします。

この前提はEから取り入れる。メトリックをSlop判定器や「Slopではない証明」にはしない。

## 本編前半：一つの例で、困りごとと引き渡し条件を決める

Platform Advisorを説明用の架空Scenarioとして用いる編集案とする。
実際の顧客成果や導入後の実測として提示せず、測定設計の考え方を示す。

### まず、VSMとMBPMのどこを見るか

全体図では、利用可能なインフラの情報探索、問い合わせ、比較観点の整理、Project Ownerとの合意形成、
利用方法の詳細調査、環境払い出し・利用開始までを追う。AIが回答する箇所で図を止めない。
次に、比較材料が合意形成へ渡る箇所をMBPMで拡大する。

| 図で見るもの | 読み取るための問い |
| --- | --- |
| Actorと受け渡し | 誰が出力を受け取り、何を判断し、何を次へ渡すのか |
| Process Time（PT） | 実際に手を動かしている作業はどこか |
| Lead Time（LT） | 着手可能になってから次へ渡るまで、どこで待ちを含む時間がかかるか |
| 手戻りとComplete & Accurate | 受け手が追加・訂正・確認をせず次の仕事を行えるか。できない時はどこへ戻るか |

MBPMの用語参照は`EXT-20260731-113601-mbpm-open-practice-library`。
VSMで全体を捉え、必要箇所をMBPMで具体化するという説明に使う。
本編ではCurrent Stateを先に見せ、変更候補と測定点を重ねる。図を描くだけで原因が確定したとはしない。

マジカの「もやもや」「技あり」のカードを図の周りに置く、本人の実践を短く紹介する。
担当者が補っている仕事、暗黙の工夫、図だけでは見えない困りごとを聞くために使う。
カードの内容を新たに作る場合は説明用と明記し、実際のインタビュー結果にしない。参照：A 8-1。

### A 8-2：何に困っているから、そのAIの使い方なのか

| 困りごとの例 | AIから欲しいOutcome |
| --- | --- |
| 情報が散らばっていて見つからない | 広く探す |
| 資料と自分たちの状況との関係が分からない | 分かるように解釈する |
| 比較観点を毎回有識者が組み立てている | 選べるように整理する |
| 選定理由の抜けや矛盾を確認したい | 本当に筋が通るか疑う |
| 判断済みの内容を繰り返し転記している | 速く作る |

参照：A 8-2、`RN-20260730-140133-ai-outcomes-and-mbpm`。
この五つは登壇用の分類候補であり、網羅的・排他的な能力分類ではない。
全項目を等しく解説せず、例では「比較して選ぶための判断材料を整理する」を追う。
まず本当の困りごとと必要品質を確認し、それにAIが有用か、どんな使い方が妥当かを考える。
AIの導入そのものを成功条件にはしない。

後続担当者へ「どんな材料があれば判断に進めますか」と聞き、引き渡しのContractを決める。
この例のContract候補は、比較観点、参照根拠、適用条件、不明点、人が判断すべき範囲、戻し先。
これは設計例であり、実際に合意された条件ではない。D 3の考え方を用い、
APIのContractにたとえつつ、入力・出力の形式だけでなく次の仕事が成立する条件まで扱う。

> 「良い提案」でも、欲しかった判断材料とは違えば、判断の仕事を増やします。
> 何を助けたいかと、何を渡せば助かるかを、先に揃えておきます。

## 本編の中心：D 6の測定点を選ぶ思考過程

6分を確保し、完成したメトリック一覧だけで終わらせない。
同じ図の対象工程、受け渡し、さらに下流を順に指し、次の順序で説明する。

1. **良くしたい仕事を指す。** 情報探索・問い合わせ準備・比較観点整理を助けたい。ならばこの工程のPT・LTをBaselineと比べる。
2. **出力の受け手を辿る。** 比較材料はProject Ownerとの合意形成で使う。根拠不足なら、その場で確認や補完が発生するのではないか。
3. **失敗がどこに現れるかを考える。** 差し戻しだけを見ると、Reviewerがその場で吸収した仕事を見落とす。初回レビューの時間、追加確認、指摘理由も見る。
4. **さらに先の利用まで見る。** 選定時の誤解が詳細調査や払い出し後に判明し、選び直しや例外対応にならないか。担当者の所感・出来事も聞く。
5. **比較できる定義と次の判断を置く。** 誰のどの案件、どの期間、どの開始・終了点を測り、どんな結果なら続ける・変える・追加確認するかを決める。

以下は図へ重ねて表示する説明案。元の測定設計は
`RN-20260807-123008-platform-advisor-effect-measurement-observation-rationale`を参照する。

| 図上の場所 | 仮説・気になること | 置くメトリックと補う情報 |
| --- | --- | --- |
| 情報探索・問い合わせ準備・比較観点整理 | 欲しい判断材料を得る仕事が減るはず | 対象工程のPT・LT・手戻り。Advisorとやり取りする時間も含む |
| Project Ownerとの合意形成 | 上流で減った仕事がReviewerへ移るかもしれない | 初回・再レビューのPT、合意までのLT、再レビュー回数、追加確認と指摘理由 |
| 利用方法の詳細調査 | 適用条件の見落としや誤解が、選び直しにつながるかもしれない | 選定に戻る手戻り、追加質問、Platform Teamの対応PT・回答LT、問い合わせ理由 |
| 環境払い出し・利用開始後 | 前段で分からなかった制約や追加作業があるかもしれない | 例外対応・修正の記録と事後ヒアリング。遅延は追跡対象を探すSignalとして使う |

詳細調査はAdvisorの対象外なので、通常の問い合わせがあるだけでは歪みと判断しない。
何が増え、何に由来したかを見る。これは元のScenarioのScopeに沿った説明である。

時間指標は、実作業時間と待ちを含むLead Timeを区別する。
工程の時間短縮、利用者が選択できたこと、Platform採用、最終的な運用費削減は別の確認対象とする。
局所の改善からBusiness Outcomeが実現したと飛躍しない。

Baselineは同じ工程境界・対象条件で用意する。件数や案件の難しさ、利用者の違いも記録する。
割合を使うなら分母・対象期間・判定者を決める。例えばComplete & Accurateは、対象の受け渡しのうち、
受け手が追加・訂正・確認なしで次の仕事を行えた件数の割合として、何を「行えた」とするかを揃える。
計測できない項目は未取得とし、想像で埋めない。閾値や削減量は今回新しく捏造しない。

> 「どこが速くなったか」と「誰に何が増えたか」を対で見ます。
> 数値だけで理由が分からなければ、受け手に聞く。これを、最初から設計しておくんです。

## 本編の結び：仮説検証として次の判断に戻す

Contractを満たす小さなパーツを作り、単体の動作、次工程との接続、利用結果を順に確かめる。
狙った効果と負担の観測から、例えば次のように判断する。いずれも実測結果ではなく説明用の分岐である。

- 対象作業が軽くなり、受け手も次へ進める：残して継続観測する。
- 作成は速くなったが、確認・補完が増えた：Contract、任せ方、出力内容、適用対象を見直す。
- 効果が見えない、または負担が許容できない：理由を追加確認し、修正または停止を判断する。

「Contractを満たしたか」「利用者の仕事が良くなったか」「受け手がどう感じたか」は分けて確かめる。
数値の改善だけでSlopではないとは言い切らず、所感と具体的な出来事を一緒に扱う。
Eの前提を回収し、Dの作って確かめる流れにつなぐ。

最後は「自分たちのPlatform Serviceの受け渡しを一つ選び、誰の困りごとかを聞き、
効果と歪みを確かめる測定点を一つずつ考えてみる」と持ち帰りを示す。
Platform Team内でAIを使う仕事にも、利用者向けのAIサービスにも同じ問いを適用する。
図、測定設計の詳細、検討の記録はRepoへ案内する。

## Session情報との対応と、次に具体化するもの

採択済みProposal（`EXT-20260730-015112-accepted-session-proposal`）は、Platform Team自身の
AI活用と、AIを含むPlatform Serviceの両方について、Value Stream上の効果と新たな確認負荷・手戻りを
確かめ、価値仮説と検証に時間を使う内容を約束している。今回の構成では冒頭と結びで両方を明示し、
主な実演はPlatform Advisorに絞る。この対応づけは編集上の整理であり、聴衆の期待を実測した結果ではない。

次のスライド具体化では、全体VSMと一箇所を拡大したMBPM、所感カード、引き渡し条件、測定点を
同じ例の上へ順に重ねる。図・カードの具体物、調査で示す指標、測定の閾値、スライド枚数は未確定。
メトリック候補の羅列で終わらず、どこを見てその候補を選んだかを説明できるか、リハーサルで確認する。
