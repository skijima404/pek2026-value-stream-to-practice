## 一本の流れ

> AIを使って仕事を速くしても、受け手が困ったり、全体の成果につながらなかったりすることがあります。
> 仕事の受け渡しと、目的への貢献・受け手の負荷を見ましょう。
> VSMとMBPMで仕事の流れを捉え、狙った改善が組織目的へつながる筋道を価値仮説にします。
> 狙った効果と悪い副作用を測り、原因を深掘りして対処します。作ったものを捨てる事態を減らすため、作る前の仮説検証も重要です。

```text
Keynoteの視聴経験を確認し、聞き手と共有できる文脈を探る
  → 自身のSlop体験とWorkslop調査で、負担と送り手への信頼低下を見る
  → AIの有無にかかわらず、仕事を渡す側には責任がある
  → バトンパスで受け渡しの条件と全体の成果を考える（Throughputへ接続）
  → 貢献度と受け手の負荷で、残す・支援する・やめるを考える
  → VSM・MBPMでPlatform選定の流れと問い合わせの負荷を見る
  → 「ミーティングゼロ」を目指し、価値仮説とPlatform Advisorを置く
  → ミーティングゼロだけでは成果・利用状況・副作用が分からない
  → 価値仮説に沿った効果、全体のThroughput、Adoption、副作用を測る
  → 測定で状態を知り、原因の深掘りを経て対処する
  → 貢献度が低い場合を通じて、作る前の仮説検証の重要性を伝える
  → 価値仮説と両面の効果測定で、AI Slopを検知・修正できるようにする
  → この資料の検討過程もRepoで公開していると案内する
```

## 1. 聞き手との共通の文脈を確認し、AI Slopの影響を示す

**対応：p.1–6。**

表題と自己紹介の後、p.3で「今日のKeynoteをみましたか？」と尋ねる。スライドには「仮説検証中」と記されている。実際の挙手と説明の切り替えは、後述の「当日の説明に関する補足」に分けて記録する。

p.4でAI Slop編に入り、自身のスライド作成に関する被害体験を話す。p.5の「4h → 12h」はその体験の図示であり、今回の資料作成全体の工数ではない。図だけでは集計条件や作業内訳は確定できないため、生成時にも具体的な内訳を補わない。

p.6ではBetterUpのWorkslop調査を紹介する。公開版で示す数値は二つ。

- 40%：直近1か月にAI Workslopを受け取ったと認識している人の割合。
- 42%：Workslopを受け取った人のうち、送り手を以前より信頼できないと感じる人の割合。

42%は回答者の割合であり、信頼度スコアの低下率ではない。受け手の負担に加えて、送り手への信頼にも影響するという話へ広げる。「次によいものを出しても信じてもらいにくい」は考えられる懸念であり、この調査が直接測定した結果として提示しない。出典は[BetterUpの原記事](https://www.betterup.com/blog/hidden-costs-workslop)と[Workslop紹介ページ](https://www.betterup.com/workslop)。

同じページには、Slopかどうかは受け取り側の主観的な判定に依存し、成果物が本当に低品質だったかを調査内で評価したわけではない、という説明がある。受け手の体験を入口に、仕事の渡し方へ話を進める。

**次へのつながり：** 受け手の負担や送り手への信頼に影響するなら、仕事を渡す側として何を確かめるべきか。

## 2. バトンパスで受け渡しを捉え、対処の判断軸を置く

**対応：p.7–10。**

AIを使っても、仕事を後続へ渡す責任は変わらない。受け手が使える状態かを確認し、困りごとがあればフォローし、よりよい渡し方を考える。

それをリレーのバトンパスにたとえる。受け取った後すぐにトップスピードへ乗れたか、想定された区間で渡せたか、そして全体のタイムが出たか。p.8では全体のタイム（Outcome）に「Throughput！」を添え、部分の動きだけでなく全体の成果を見る話へつなぐ。

スピードが合わない、想定した場所にバトンがない、受け手の準備ができていない、といったずれがあると成果へつながらない。ただし、片方が悪いと決めつける話ではなく、実際の受け渡しを調べないと理由は分からない。

対処を考える軸として、目的への貢献度と受け手の負荷を組み合わせる。

| 貢献度 | 受け手の負荷 | スライドで示す方向 |
| --- | --- | --- |
| 高い | 低い | 理想の状態として残す |
| 高い | 高い | 改善・支援し、受け手がパンクしないようにして残す |
| 低い | 高い | 作らない、またはリタイアする。リリース済みなら即対応 |
| 低い | 低い | 成果へ貢献しないので作らない、またはリタイアする |

**次へのつながり：** 部分的に速くなっただけでは全体の成果は分からない。仕事の流れ全体を捉え、可視化・計測・改善するVSMへ進む。

## 3. Value Streamを説明し、先に「あるある」の事例を見せる

**対応：p.11–18。**

Value Streamを、価値が必要になってから必要な人へ届くまでの流れとして説明する。p.13のValue Stream Managementの説明では、流れ全体の効率にThroughputという語を添え、可視化・計測・改善する取り組みとして紹介する。「速かったか」「使えるものになったか」「後で問題が起きなかったか」という問いを、企画から運用までの図に載せる。

ここで、あるあるパターンを先に見せ、その後で解説すると予告する。以降のPlatform Advisorは説明用の架空事例であり、実在案件の成果報告ではない。

事例では、組織の目的、作戦、チームの目的を分ける。

- 組織は、限られた人的資源を価値創出へ集約したい。
- コンテナオーケストレーションによる運用の自動化・高度化を、そのための作戦とする。
- Platform Engineeringチームには、コンテナオーケストレーションの利用促進が求められている。

チームはまず、プラットフォームを選ぶまでの流れをVSMで捉える。情報収集、問い合わせ、比較観点の整理、意思決定、ADR記録、申請方法の調査・確認が並ぶ。

p.17で「わからない点をまとめて質問する」工程を、解決すべき課題の候補として指す。p.18ではMBPMを使ってその工程を拡大し、開発者、窓口担当、Enabling担当のやり取りを見る。事例の設定では、状況を把握して答えるためにミーティングが必要で、問い合わせのLTは1週間、再検討や追加質問による手戻りが50%とされる。

**次へのつながり：** この負荷を減らし、短時間で安全に選べるようにしたい。チームがどんな価値と目標、解決策を置くかを見せる。

## 4. 「ミーティングゼロ」と価値仮説、Platform Advisorを置く

**対応：p.19–21。**

目指す価値は、プラットフォーム選定の負荷を軽減し、短時間で安全な選択を可能にすること。その目標として「ミーティングゼロ」を置く。

この局所の改善を組織の目的へつなぐ見込みを、価値仮説として見せる。

```text
情報収集・選定の負荷が減る
  → コンテナ基盤の採用が進む
  → 運用の自動化が進む
  → 人の手が空く
  → 必要な仕事へ人的資源を再配置できる
```

p.20の赤枠は、最初の二つを「このPlatform Engineeringチームのスコープ」として示している。組織目的までの見込みと、チームが直接担う範囲を区別する。

そのうえで、解決策としてPlatform Advisorを紹介する。AIチャットボットがプラットフォームの選び方、メリット・デメリット、技術を説明する。ミーティングの調整を減らし、開発者の理解度に合わせて説明することで、選定の負荷を減らそうとする。

**次へのつながり：** ここまでならもっともらしく見える。しかし、ミーティングがゼロになったら本当に成功なのか。ここから効果測定の解説へ入る。

## 5. 「ミーティングゼロ」の不足を、効果測定の問いへ変える

**対応：p.22–27。**

ミーティングゼロだけでは、欲しい成果が出たか、選定が進んだ結果なのかそもそも候補から外れたのか、副作用が出ていないかが分からない。

先ほどの二軸の図を再掲し、効果測定によって、成果への貢献と受け手の負荷のどこに該当するかを確かめると説明する。

効果測定を「活動目的に対するビジネス的なテストケース」にたとえる。

- 正常系：狙った効果が出ているか。
- 異常系：悪い副作用を抑えられているか。

まず正常系として、p.20の価値仮説をp.26で再掲する。同じつながりに確認の問いを載せる。

- チャットボットは情報収集の時間を短縮できているか。
- 情報収集が簡単になると、本当に基盤の採用が増えるか。
- 情報収集の時間短縮は、Value Stream全体のThroughput向上につながっているか。

自動化に進む使われ方をしているか、作業工数が減るかという後続の問いも薄い色で残る。チームの直接の範囲を中心に話しながら、上位目的へつながる条件が別にあることを示す。

さらにAdoptionも確かめる。役立っているからミーティングがなくなったのか、基盤自体が無視されているからなくなったのかを区別するため、認知度、利用数、利用者の感想を見る。

**次へのつながり：** 狙った改善が起きても、別の人や工程が困っているかもしれない。次に異常系として副作用を見る。

## 6. 受け渡しと運用までを追い、副作用を見つける

**対応：p.28–30。**

価値仮説の図に、副作用を確かめる問いを重ねる。質の悪い回答が問題を起こしていないか。情報収集や選定の速度が急に変わって、困る人がいないか。

副作用を探す場所として、人と人とのハンドオーバーに着目する。p.29では、開発者の観点整理・資料作成から、承認者との意思決定へ進む図を使い、「承認が降りにくくなっていないか」と問う。問い合わせ窓口の工程とは別の、後続の受け渡しを見せている。

さらに、Value Streamの認識が短いと、リリース後の悪化を見落とす。p.30では企画から運用までの図に戻り、デプロイ時の想定外のトラブル、インシデント傾向、SLA実績、運用工数を確認対象として挙げる。

**次へのつながり：** 測定で良化・悪化を捉えられても、それだけで原因までは分からない。対処に進むには、もう一段深掘りする。

## 7. 原因を深掘りし、作る前の仮説検証と作った後の効果測定をつなぐ

**対応：p.31–35。**

二軸の図をもう一度示し、効果測定で分かるのは「どこに該当するか」までだと区切る。

バトンパスの失敗例を再掲し、同じように受け渡しがうまくいかなくても、速度、位置、受け手の状態など理由は異なることを思い出してもらう。実際に何が起きたか、なぜ起きたかを深掘りし、その事象に合った対処をする。

p.33では「成果への貢献度が低い場合」に話を絞る。どの段階で間違ったかによって、対処できる範囲が異なると説明する。

- 価値仮説レベルで間違った場合：捨てざるを得ない可能性が高い。
- ソリューションの企画段階で間違った場合：捨てざるを得ない可能性が高い。
- 実装レベルで間違った場合：修正できるかを確認し、できなければ捨てざるを得ない。

このため「作る前に検証！！」と、仮説検証の重要性を置く。貢献度が低ければ必ず全て捨てるという断定に変えず、修正できる場合との区別を保つ。公開版は具体的な検証手法までは説明していない。

**まとめへのつながり：** 作る前には価値や解決策の見込みを確かめ、作った後には狙った効果と副作用を測る。問題が起きたら原因に合った対処をする。

p.34の区切りを経て、p.35の三点へ着地させる。

1. AI Slopを検知して修正できるよう警戒を怠らず、価値仮説と効果測定を利用する。
2. 目的へ至る因果のつながりを価値仮説として置き、効果や局所最適の有無を確かめられるようにする。
3. 効果測定では、狙った効果と悪い副作用の両方を測る。

以前の会話にあった「AI Slopは完全には防げない」を、公開版の見出しとして置き直さない。この版は、検知・修正できるようにする行動をまとめにしている。

## 8. 資料そのものの検討過程をRepoへつなぐ

**対応：p.36–37。**

「このプレゼンにもAI Slopが紛れていないか」という問いで、話をこの資料自身へ戻す。

どこでAIを使い、どう見直したかをたどれるように検討記録を公開していると紹介する。調査資料、話さなかったネタ、採用しなかった案も含むRepoへQRコードで案内し、Thank youで終える。記録が公開されていることを、AI Slopがないという保証にはしない。

## スライド生成時に保持する関係と境界

以下は公開版と登壇者の指定を再現するための入力整理であり、新しい話題の追加指定ではない。

1. **反復には役割がある。** バトンパスは受け渡しと全体の成果を示し、後で原因深掘りへ戻る。二軸の図は判断基準（p.10）、測定対象（p.24）、原因は別途調べるという限界（p.31）の順に使う。同じ図として機械的に削らない。
2. **価値仮説の同じ筋道を使う。** p.20で因果の見込みを置き、p.26で狙った効果、p.28で副作用の問いを重ねる。情報収集の短縮だけで人的資源の再配置が実現したと飛躍させない。
3. **架空事例と調査値を分ける。** Platform AdvisorのLTや手戻りは説明用の設定。BetterUpの数値は外部調査で、出典と分母を保つ。4h → 12hは本人の別の体験である。
4. **Throughputを入れた意図を保つ。** Keynoteとの接続に用いた語である。LT、全体のタイム、Throughputを同一の定量指標として自動変換したり、測定していない値を補ったりしない。
5. **二つの対処をつなぐ。** 貢献度が高く負荷も高いものは改善・支援して残す。貢献度が低い場合は誤りの段階と修正可能性を見て、作る前の検証にも戻る。「Slopと呼ばれたら全部捨てる」にはしない。
6. **資料の内容と話し方を分ける。** Keynoteへの具体的な言及や章間のつなぎは話す側の補足として扱う。本書の段落を全てスライド本文に載せる必要はない。
